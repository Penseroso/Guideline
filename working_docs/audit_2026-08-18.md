## 3. Governance overhead

`working_docs/decisions.md` contains **49 unique DEC-XXX entries** (DEC-001 through DEC-048, 446 lines). `working_docs/review_log.md` contains **12 unique REV-XXX entries** (through REV-011, 249 lines). Combined: **61 governance records**.

These 61 governance entries were produced to govern approximately **162 structured semantic objects** (93 KnowledgeRecords + 14 QuantitativeCriteria + 46 Conditions + 9 CrossReferences) plus 8 derived-layer records (4 AmendmentMapping + 4 EffectiveRecord), i.e. roughly **1 governance entry for every 2.5-2.7 structured records produced.** This is a genuinely high governance-to-output ratio: the project has spent substantial deliberation cycles per unit of actual archived content. That is a defensible cost for establishing a correct, hard-to-change data model (see §7), but it is a real signal that content-production velocity at this ratio would not scale to cover even one full guideline, let alone a multi-guideline archive, without either a lighter review process or much more automation.

## 4. Schema/data-model fitness for a chatbot/RAG product

Read `working_docs/schema.md` (347 lines), `structured_data/schemas/guideline_bundle.schema.json` (443 lines), and all files under `structured_data/schemas/derived/` (`core.schema.json` + 9 files under `artifacts/` + `profiles/ich.schema.json`).

**Granularity vs. direct retrieval consumption.** The model is `Document -> Section -> SourceUnit -> {KnowledgeRecord, QuantitativeCriterion, Condition, CrossReference}` (`working_docs/schema.md:93-316`). `SourceUnit.source_text` is the smallest addressable text unit, but it is fragment-level (a single paragraph, list item, table cell, or footnote — `working_docs/schema.md:136`), not a retrieval-ready chunk. A RAG layer could not embed `SourceUnit.source_text` directly and expect coherent answers for most questions — related SourceUnits (e.g., a table row split across multiple `table_cell` units, or a KnowledgeRecord spanning multiple SourceUnits via `source_unit_ids`) would need to be re-assembled into passages first. This is a real, non-trivial transformation step, not a data problem — the underlying links needed to do the reassembly (`KnowledgeRecord.source_unit_ids`, `SourceUnit.related_source_unit_ids`, `SourceUnit.section_id`) already exist.

**What helps citation-grounded answering (present today):**
- Page-level provenance on every SourceUnit: `trace.pdf_page_index_zero_based`, `trace.printed_page_label`, both nullable with an explicit `*_status` field rather than a guessed value (`working_docs/schema.md:157-168`) — this is exactly the kind of hard citation anchor a hallucination-resistant chatbot needs, and it is already populated and validated (e.g., `structured_data/pilots/m10_phase2_table_pressure.json` source_units carry `pdf_page_index_zero_based: 46, printed_page_label: "47"`).
- `review_status` (`unreviewed`/`needs_review`/`reviewed`) exists on every semantic object, so a retrieval layer could filter to `reviewed`-only content trivially, or surface confidence to the user.
- `source_file_checksum` on `Document` (`structured_data/pilots/m10_3_2_5_2.json:10`) ties structured data to an immutable source artifact, useful for audit trails.

**What would make it harder / needs work:**
- CrossReferences are mostly unresolved: 4 of 9 have `resolution_status: unresolved` and 4 more `needs_review` (only 1 fully `resolved`). A chatbot asked "what does Section 8 require" via a cross-reference from a structured record could not follow that link today for most cases.
- 1 KnowledgeRecord and 1 Condition are still `needs_review` — small in absolute count, but a reminder that "reviewed" is not yet the default state at document scale.
- The schema is explicitly scoped as a preservation/archival contract, not a retrieval contract: `working_docs/schema.md:16` states model 0.2.0 "does not define full-guideline extraction, database storage, search, embeddings, RAG, regulatory decision logic, or an application interface." That framing is accurate as of today — none of those layers exist in this repo (§6).

**Multi-document / multi-guideline fitness.** The schema does *not* assume a single-document archive at the structural level: `Document.guideline_code`, `Document.issuing_body`, and `CrossReference.target_type=guideline` / `target_document_label` (`structured_data/schemas/guideline_bundle.schema.json`, `working_docs/schema.md:272-291`) already anticipate multiple guidelines and cross-document references, and the two guidelines present (M10, S6(R1)) already validate together via `npm run validate:pilots` without collision (confirmed: "Validated 5 pilot bundle(s)" spanning both documents, `working_docs/schema.md:34` self-contained-bundle rule tested by `test/validate_structured_data.test.js` "valid two-bundle validation passes"). The derived layer adds an explicit `GuidanceFamily`/`DocumentEdition`/jurisdiction model (`structured_data/schemas/derived/artifacts/guidance_family.schema.json`, `edition_source.schema.json`) intended for cross-jurisdiction, cross-edition lifecycle tracking (FDA/EMA-style multi-authority framing is structurally anticipated, though no non-ICH profile schema exists yet — only `profiles/ich.schema.json`).

## 5. Code quality notes (secondary)

Skimmed `scripts/validate_structured_data.js` (383 lines), `scripts/validate_pilots.js` (48 lines), `scripts/validate_derived.js` (590 lines), `scripts/validate_legacy_derived.js` (632 lines), and `test/*.js` (1,298 lines combined).

- No hard-coded absolute paths found; all scripts resolve `ROOT` via `path.resolve(__dirname, "..")` (`scripts/validate_structured_data.js:5`, `scripts/validate_derived.js:5`) — portable across machines/OS.
- Consistent error-reporting convention (`addError`/`location` helpers duplicated near-identically in `validate_structured_data.js:36-45` and `validate_derived.js:42-51`) — minor duplication, low risk.
- `scripts/validate_derived.js` and `scripts/validate_legacy_derived.js` are two parallel, largely non-overlapping ~600-line validators for two different generations of the same conceptual layer (amendment mapping / effective record). This is the more significant maintainability flag: the repo is currently carrying two full validator implementations for the "same" concept (legacy shape, which holds the only real S6(R1) derived data, vs. contract shape 0.1.0, which is fully tested but has no real data). This will need a deliberate migration or explicit sunset decision rather than indefinite parallel maintenance.
- Test coverage is proportionally large and specific (126 tests covering edge cases like cross-family jurisdiction mismatches, cycle detection in predecessor chains, duplicate ID detection across artifact types) — this is a strength, not a concern.
- `scripts/validate_pilots.js` auto-discovers files under `structured_data/pilots/` recursively rather than relying on a hard-coded file list (`scripts/validate_pilots.js:9-23`), so new pilot files are picked up automatically by both the npm script and CI.

## 6. Gaps blocking a shippable chatbot

- [ ] **No retrieval/index layer.** No vector store, keyword index, or any retrieval code anywhere in the repo. `grep -riE "embed|vector|chunk|retriev"` across `scripts/`, `structured_data/schemas/`, `package.json` returns zero matches.
- [ ] **No embeddings.** No embedding-generation code or embedding-model dependency. `package.json` dependencies are exactly one package: `ajv@^8.17.1` (JSON Schema validation only).
- [ ] **No API/backend.** No server framework (no `express`, `fastify`, etc.), no route files, no API directory anywhere.
- [ ] **No UI.** No frontend framework, no HTML/React/Vue files, nothing resembling a chat interface.
- [ ] **No eval/hallucination-measurement framework.** No test-set, no answer-grading harness, no groundedness metric anywhere — the 126 tests are all schema/structural validation, none evaluate generated answers.
- [ ] **No chunking strategy.** SourceUnit is fragment-level (paragraph/list-item/table-cell/footnote); no defined strategy exists for assembling SourceUnits into retrieval-sized passages (see §4).
- [ ] **Coverage too narrow to be useful standalone**: 2 of ~70 M10 sections and 4 of ~41 S6(R1) sections are genuinely structured (§2) — a chatbot scoped to only this data could answer meaningfully on species selection and two bioanalytical-validation subsections, and essentially nothing else.
- [ ] **Multi-guideline support is structurally proven but only lightly exercised**: schema and validator handle 2 documents today (§4); nothing demonstrates behavior at 5+ guidelines or with actual cross-guideline CrossReferences resolved end-to-end (all current cross-guideline-shaped references are `unresolved`/`needs_review`, §2).
- [ ] **No FDA/EMA (non-ICH) profile.** Only `structured_data/schemas/derived/profiles/ich.schema.json` exists; the `regulator_profile` enum in `core.schema.json:43-46` only allows `"core"` or `"ich"`.
- [ ] **Derived-layer production data uses the legacy schema, not the newer contract schema** — the two never merged (§1, §5), so any retrieval work reading `structured_data/derived/*.json` today reads legacy-shaped data only.

## 7. Reusable strengths

- **Page-level source traceability is real and validated, not aspirational.** Every SourceUnit carries `pdf_page_index_zero_based` + `printed_page_label` with independent status flags, checked against the actual PDF byte content (`working_docs/pdf_assessment_M10.md`, `working_docs/pdf_assessment_S6_R1.md` document exact PDF page counts, 59 and 23 respectively, and page-index boundaries per Part). This is a direct asset for citation-grounded answering — a chatbot can cite "M10 §3.2.5.2, PDF page 14" today, sourced from real structured fields.
- **Explicit modality/record_type separation** (`KnowledgeRecord.record_type` independent from `modality`, `working_docs/schema.md:184-207`) lets a retrieval/generation layer distinguish a binding requirement from a description or example without re-deriving that classification from raw text — 60 of 93 KnowledgeRecords are already tagged `recommendation`.
- **Condition/exception modeling is genuinely structured, not folded into free text**: 46 Condition objects with `condition_type` (`applicability`/`scope`/`precondition`/`exception`) and `applies_to_ids` linking back to the exact KnowledgeRecord/QuantitativeCriterion/SourceUnit they qualify (`working_docs/schema.md:247-270`). This is exactly the kind of structure that prevents a chatbot from stripping "except when..." caveats out of an answer.
- **Closed, validator-enforced vocabularies** for `record_type`, `modality`, `review_status`, `value_status`, `condition_type`, `target_type`, `resolution_status`, `amendmentRelationType` — all enum-checked by JSON Schema plus cross-checked by the reusable validator, so the underlying data cannot silently drift into free-text ad-hockery.
- **Validation discipline is real and currently green**: 126/126 tests, 3 separate validation scripts, all passing (§1), with tests specifically targeting adversarial/edge cases (cycle detection, cross-jurisdiction leakage, duplicate IDs across artifact types) rather than only happy-path checks.
- **Exact-fraction preservation** for quantitative criteria (`QuantitativeCriterion.value_fraction`, `working_docs/schema.md:229-243`) avoids silently lossy decimal conversion of source expressions like "2/3" — a small but concrete anti-hallucination design choice.

## Net assessment

The repository is a small, rigorously validated, and honestly self-documented data-preservation layer, not yet a product. All validation currently passes (126 tests, 3 validators, 5 pilot bundles), but the actual reviewed content covers roughly 6 leaf sections out of ~111 combined sections across the two guidelines present — under 10% coverage of two guidelines, with zero others attempted. The 61-entry governance trail (49 decisions, 12 reviews) shows real deliberative rigor per record but implies a production rate that would not scale to broader coverage without changing the process. The data model itself is a genuine asset for a hallucination-resistant chatbot — page-level traceability, modality/record-type separation, and structured conditions are already real and validated — but it is a source-of-truth archive schema, not a retrieval schema, and every layer a chatbot needs on top of it (chunking, embeddings, index, API, UI, eval harness) is completely absent from the repository today, confirmed by direct grep and dependency inspection rather than by trusting prior planning-doc claims.
