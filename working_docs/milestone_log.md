- **Option A fully working end-to-end today, zero LLM calls**: `npm run chat` answers real questions with accurate citations from the 5 pilot bundles.
- **Option B built and unit-tested with a mocked client** (generation → entailment check → refuse-if-not-entailed), but never run against a real model — no API key configured yet.
- Two real bugs found and fixed via actual testing, not just design review: (1) a ranking bug where preferring `QuantitativeCriterion`/`Condition` over `KnowledgeRecord` on "near-max" score used too loose a margin, letting a barely-relevant criterion (score 1) outrank a clearly better-matched record (score 2) — fixed to exact-tie-only preference; (2) `engine/cli.js` raced `process.exit()` against an in-flight async answer when given piped multi-line input, silently dropping output — fixed with an explicit FIFO promise queue.

Stored only in local `.env` (now gitignored — `.gitignore` previously had no `.env` entry at all), never echoed back, user was told to treat it as compromised; they revoked and re-issued it themselves outside the chat. `.env.example` documents both provider keys; `.env` holds empty placeholders pending the user filling it in directly (not via chat).
- **Real dry-run measurement (2026-08-18), OpenAI GPT-5.6 Terra, live API, M10 §3.2.5.2 vs. the existing human-reviewed bundle**: extracted 14/14 KnowledgeRecords (record_type 100% match, modality 100% match including the one non-default `modality=other` case), 11/12 QuantitativeCriteria (91.7% recall), 5/7 Conditions (71.4% recall) — **zero fabricated or wrong values across all 30 extracted objects; every failure mode was under-extraction (a real fact missed), never a wrong fact asserted.** The 2 missed Conditions were an idiosyncratic pattern (using `condition_type=applicability` to tag a subsection's scope rather than a true "if X" clause) rather than a dangerous miss. Adversarial check: a deliberately fabricated claim ("accuracy must be within 5%" against a source that says 15%) was correctly caught as `entailed: false` by the verification agent.
- **Open finding, not yet resolved — verification granularity mismatch**: the verification agent, checked against the record's own extracted `source_text` (a deliberately minimal verbatim quote) or even the full source paragraph, flags some *correct* narrowly-scoped criteria as `entailed: false` when they don't restate a sibling exception modeled in a *separate* record (e.g. the general 15%-accuracy criterion doesn't restate the LLOQ 20% exception, which is correctly split into its own criterion per `working_docs/schema.md`'s own "use multiple QuantitativeCriterion records for a general rule plus an exception" guidance) — `claimTextFor()` builds a bare `parameter/comparator/value/unit` string that's narrower than what `query_router.js`'s `formatAnswer()` actually shows users (which includes `denominator_or_reference`). Not patched yet: needs a decision (enrich the claim text vs. relax the verifier's strictness for extraction-time checks vs. accept the current stricter-than-necessary behavior as a safety margin, since it doesn't affect user-facing answers today) rather than a guess. Does not block M1 — this only affects extraction-time dry-run accuracy scoring, not what's shown to end users.
- Real bugs found and fixed via the live API (not just mocks): (1) submitted extraction schema still contained unresolved `$ref`s into a `definitions` block the API never received — OpenAI rejected it outright; fixed with a `dereference()` pass. (2) OpenAI strict-mode JSON Schema rejects `oneOf` (used for nullable `value_fraction`) — rebuilt as `type: ["object","null"]`. (3) GPT-5.6 is a reasoning model: `max_completion_tokens` covers hidden reasoning tokens *and* visible output; the adapter's 1024 default was fully consumed by reasoning on a real section (`finish_reason: "length"`, 0 content characters) — extraction now requests 8000.
- Model choice: GPT-5.6 Terra (not Sol) for extraction — Sol is priced/marketed for "hard problems, long autonomous tasks," not well-scoped single-section structured extraction; escalate only if a real measured accuracy gap (not a guess) shows Terra falling short.
- **Prompt-tuning attempt on the under-extraction finding (2026-08-18), 3 versions measured on the same section (M10 3.2.5.2) — not a schema problem, confirmed a prompt problem, but not yet solved cleanly**:
  - v1 (original): KR 14/14, QC 11/12, Cond 5/7. Diagnosis: the schema already fully supports every missed record (the human-reviewed archive has them under the same schema) — the extraction prompt just never told the model to keep decomposing a sentence after it already produced a KnowledgeRecord from it.
  - v2 (added "be exhaustive, don't stop at the first record type that fits"): KR 14/14, QC **12/12** (fixed), but Cond regressed to 10/7 — the model started emitting duplicate near-identical Conditions (e.g. "except at the LLOQ" twice) instead of one Condition shared via `applies_to_ids` across both records it qualifies.
  - v3 (added "don't duplicate — merge shared conditions via applies_to_temp_ids, don't invent conditions for rationale phrases"): fixed the LLOQ duplication, but QC **regressed to 10/12** and Condition count grew to 12 via a *new* failure mode — fragmenting plain descriptive qualifiers ("at each concentration level") into spurious Condition records.
  - **Reverted to v2's core instruction** (exhaustiveness, without the v3 anti-duplication addendum) as the current checkpoint: non-monotonic results (QC 11→12→10, Condition 5→10→12) across 3 versions on one section is not reliable signal to keep tuning against — needs a multi-section eval before another attempt, not more single-section prompt patching. `engine/extraction_agent.js` records this history inline as a comment so the next attempt doesn't repeat it blind.
- **Multi-section dry-run (2026-08-18), all 10 non-empty sections across all 5 pilot bundles, same v2 prompt**: aggregate KR 120/93, QC 20/14, Cond 60/46 — extraction now runs *over* the human baseline in aggregate, the opposite direction from the single-section result. Three important qualifications, not just a headline number:
  1. **Real, measured run-to-run variance**: re-running the *same* section (M10 3.2.5.2) with the *unchanged* v2 prompt produced KR 19/14 and Cond 12/7 this time, versus KR 14/14 and Cond 10/7 in the earlier single-section test. Same code, same input, different output — the model is non-deterministic enough that a single run is not reliable signal, which retroactively means the earlier "v1→v2→v3" prompt comparison (`git log` `ddb70f5`) was likely confounded by run-to-run noise as well as by the prompt edits themselves. Multiple runs per condition are needed before trusting any future prompt-tuning comparison, not just multiple sections.
  2. **Baseline-quality caveat**: 2 of the 5 bundles (`m10_phase2_table_pressure.json`, `m10_phase2_reference_condition_pressure.json`) are documented structural probes, *not* exhaustively reviewed canonical bundles (`working_docs/schema.md`, DEC-020) — their low real counts (e.g. section `ich_m10.sec.8_2`: 1 real KR) reflect narrow probe scope, not an exhaustiveness ceiling. Comparing extraction output against them as if they were complete ground truth overstates "over-extraction" on those 3 sections; only the 7 sections from the 2 fully-reviewed bundles (`m10_3_2_5_2.json`, `m10_6_1.json`, `s6_r1_species_selection.json`) are trustworthy accuracy baselines.
  3. **The one finding that actually matters found this way**: on `ich_m10.sec.6_1` (a real, fully-reviewed section), the extraction agent invented a `QuantitativeCriterion` (`parameter: "within-run accuracy and precision determination", comparator: "at_least", value: 1`) from source text that says partial validation "**can range** from as little as one ... determination, to a nearly full validation" — a genuine semantic distortion (descriptive range turned into a normative minimum), not just a miscount. **`verification_agent.verifyClaim` correctly caught it**: `entailed: false`, with the accurate reason that the source describes a range, not a requirement. This is the first real, live-API confirmation that the two-stage design (extraction can be wrong; a separately-framed verification check catches it) works as intended — the architectural bet in `product_roadmap.md` §2.5.1 held up under an actual adversarial-by-accident case, not a synthetic one.
- **Reprioritization based on this evidence**: further single-shot prompt tuning is not a good use of the next step (finding #1 above shows it isn't reliable signal without repeated runs, which multiplies cost). More valuable: wire `verification_agent` into `extraction_agent`/the pipeline as an automatic post-draft filter (currently they're only glued together by hand in ad hoc test scripts, not integrated), so a distortion like the one just found gets caught and flagged automatically instead of requiring a human to spot-check by hand.
- **Extraction+verification pipeline integration (2026-08-18)**: built `engine/pipeline.js` (`extractAndVerifySection`, `verifyDraft`) — extraction now auto-verifies every drafted object and sets `review_status` per §2.5.1's redefinition (`reviewed` = passed extraction+verification, `needs_review` = failed, never dropped, rejection reason kept in a parallel report, never added as an extra field on the record itself since the archive schema is closed). Considered but explicitly deferred a bounded retry-with-feedback loop (verification failure → feed the rejection reason back to extraction → one retry → re-verify) — real value, but decided the immediate priority was closing the existing manual glue-code gap first, not adding self-correction on top of it; retry risks the same regression pattern already seen in the v1→v2→v3 prompt-tuning cycle (fixing one thing by breaking another) unless it's tightly bounded, and needs its own evaluation before adding.
- **Real bug found and fixed via this integration, live API, on `ich_m10.sec.6_1`**: the previously-found semantic distortion (a descriptive range — "can range from as little as one ... to a nearly full validation" — turned into a normative `QuantitativeCriterion` with `comparator=at_least, value=1`) was verified as `entailed: true` (a **false negative** — the dangerous direction, letting a distortion through as "reviewed") on the first pipeline run, even against the *full* SourceUnit paragraph, on both Luna and Terra. Root cause isolated by direct comparison: `verification_agent.claimTextFor()`'s bare `"parameter comparator value unit"` rendering (e.g. `"... at_least 1 determination"`) doesn't assert normative force explicitly enough — the verifying model read "at_least" as merely compatible with the low end of a described range, not as an asserted requirement. Rephrasing the same claim as `"... must be at least 1 ... (this is a required minimum, not merely an observed or possible value)"` against the identical source text was correctly rejected (`entailed: false`) on the same model. **Fixed**: `claimTextFor` now renders `at_least`/`not_exceed`/`within` with explicit "must be/must not exceed" + parenthetical normative framing instead of the bare comparator word. Re-ran the same section live after the fix: the same criterion now correctly lands on `needs_review`. This is the second real, live-API-confirmed case (after the first one found by hand) of a genuine extraction distortion — this time the fix was to the *verification* side, not extraction, since the schema/data was never the problem in either case.

- **Ground-truth recall/completeness audit (2026-08-18)**: earlier fidelity work (this file, above) only checked precision of the 3 fully-reviewed pilot bundles (is what's there correct) — never recall (is everything that should be there actually there). A subagent audit filled that gap: re-read the source PDF pages against every existing `SourceUnit.source_text` and its linked records. Result: `m10_3_2_5_2.json` — 0 omissions, fully complete. `m10_6_1.json` — 0 clear-cut, 3 debatable (stylistic judgment calls, left as-is). `s6_r1_species_selection.json` — **13 clear-cut omissions, 5 debatable** — roughly 75-80% complete on `KnowledgeRecord` recall specifically, with a consistent pattern: short descriptive/rationale clauses ("can provide," "is optimised when," "it should be noted that," clause-final elaborations after a comma) embedded inside longer paragraphs were systematically dropped even though neighboring sentences in the same paragraph were captured. `QuantitativeCriterion`/`Condition` coverage was much stronger (1 clear numeric miss out of ~28 correctly-extracted quantitative/condition records). **This is the same failure pattern already observed in the model's own extraction attempts** — the original human review and today's LLM extraction both under-extract short embedded descriptive clauses. That's evidence this specific recall gap is a genuinely hard part of the task, not specifically an LLM weakness.

The 5 debatable candidates were deliberately left out — genuine stylistic judgment calls, not confirmed omissions. `npm run validate:pilots` and all 187 tests pass after the additions; diff confirmed exactly 13/1/1 new records added, nothing else touched.
- **Debatable candidates resolved (2026-08-18)**: of the 5 debatable candidates, #14 (compound description+recommendation sentence) was merged into the existing `ich_s6_r1.kr.part1.3_3.009` rather than split or given a new "mixed" `record_type` — the schema doesn't need a dual-type field; compound predicates already have a precedent (`kr.part2.2_2.006`) of living in one record's `action`/`original_modal_text`. #15 was reclassified from debatable to a real omission on review (an anaphoric "these" sentence still carries independent definitional content — added as `ich_s6_r1.kr.part1.3_3.021`). #16-18 were confirmed as deliberate non-extraction, not omissions, and that judgment is now written down in `working_docs/schema.md` ("Deliberate non-extraction") so future recall audits don't re-flag the same three patterns (narrative scene-setting, incidental parentheticals, concessive framing) as debatable every time.
- **Verification-agent regression chain, found and fixed live in one sitting (2026-08-18) — because it reproduced 100%, not because it was rare**: a full-scale re-verification of the now-complete M10 3.2.5.2 ground truth (33 real records) surfaced that the "must be at least N" fix above was itself a systematic false-negative generator, not an isolated case: 27/33 real, correct records were being rejected. Because the failure reproduced on every run against the same input (not randomly), root cause was findable by cheap, targeted ablation — the same principle used to find the original distortion — rather than needing statistical sampling across many runs. Three real, sequentially-discovered causes, each verified live before moving to the next:
  1. **Modality/comparator conflation**: `comparator` (`at_least`/`not_exceed`/`within`) is a math relationship, not a regulatory modality (`must`/`should`/`may`) — that lives on the linked `KnowledgeRecord`, which the claim construction never had access to. Hardcoding "must" asserted stronger force than the source's actual "should," and got correctly rejected for it. Fixed: `claimTextFor` no longer names a modal verb at all — asserts "this is the specified criterion value, not merely illustrative" instead.
  2. **Verifying against the criterion's own minimal `source_text` instead of the full `SourceUnit`**: the narrow quote routinely omitted the parameter noun itself (e.g. "accuracy") when it sat earlier in the sentence than the number. Fixed: `verifyQuantitativeCriterion` now verifies against the full SourceUnit paragraph. This is the same principle as Anthropic's "Contextual Retrieval" (give a fragment its surrounding context before judging it) — here achieved by using the real, already-preserved full source text rather than an LLM-generated context summary, since the schema never discarded that context to begin with.
  3. **Sibling general-rule/exception records** (deliberately split per `working_docs/schema.md`'s own general-plus-exception guidance) were rejected for not restating each other. Fixed with two changes verified not to reintroduce the original distortion: (a) `verification_agent.js`'s system prompt now explicitly permits a claim to cover only one of several related criteria in the same source paragraph; (b) `claimTextFor` now appends `denominator_or_reference` ("applicable to: ...") so an exception/special-case criterion's claim states its own scope instead of reading as an unqualified general rule.
  4. **Same sibling-condition problem, KR side**: 4 of the 6 remaining failures were `KnowledgeRecord`s qualified by their own `Condition` (via `Condition.applies_to_ids`) that the claim never stated, reading as unconditional and getting correctly rejected — the exact same pattern as fix 3, just not yet applied to `KnowledgeRecord`. Fixed identically: `verifyKnowledgeRecord` now looks up applicable `Condition`s and appends their text to the claim.
  - Net result on the same 33-record ground truth, same order fixes were applied: 22/33 → 24/33 → 27/33 → **30/33 entailed (91%)**. The 3 remaining failures are a genuinely different kind of problem, not a verification-prompt bug: compound/nested criteria where one number qualifies another within a single source sentence (e.g. "at least 50% ... within ±15%") — `QuantitativeCriterion`'s single parameter/comparator/value design can't cleanly represent two entangled numeric facts in one record. This needs schema-level thought, not another prompt tweak, and is intentionally not pursued further this session — a different category of problem than the four fixed above.
  - **Answers the "is this a structural RAG limitation" question directly**: no — none of these three bugs were about retrieval. They were entailment/NLI judgment errors on regulatory modal language (must/should/may, general-rule-vs-exception scope), which is a known-hard, actively-researched NLI subcategory independent of RAG architecture — it would occur in any system trying to automatically verify normative claims, RAG-based or not. Not "solved" in general (state of the art still needs exactly this kind of targeted, domain-specific calibration), but demonstrated tractable for our specific failure modes through cheap, reproducible, live ablation.
- **Multi-signal sibling grouping for `QuantitativeCriterion` claims (2026-08-18)**, addressing the "3 remaining failures" from the regression chain above (compound/nested criteria splitting one entangled statement, e.g. M10 3.2.5.2 `qc.010`/`011`/`012`): `engine/pipeline.js` now groups a criterion with siblings via a list of independent relational signals (`SIBLING_SIGNALS`, deliberately a list, not a hardcoded pair, so a future signal can be appended) — (a) overlapping `condition_ids`, and (b) same `knowledge_record_id` **plus** an equal `condition_ids` set — and appends their values to the claim as "jointly-applicable." Also fixed the sibling qc.004-type case: `verifyQuantitativeCriterion` now looks up the linked `KnowledgeRecord`'s `original_modal_text` and surfaces it in the claim instead of assuming a fixed strength. Both changes verified three ways before trusting them: (1) mocked unit tests, including a **held-out synthetic compound-criteria case** invented for this fix, not drawn from real M10/S6 data (a fictitious "recover between 85% and 115%, with %CV not exceeding 10%" sentence) — proves the mechanism generalizes rather than re-solving one memorized case; (2) live re-verification of the real M10 3.2.5.2 ground truth; (3) live re-verification repeated a second time to separate real effect from Luna's already-documented non-determinism.
  - **A real, self-inflicted bug found during step (2) and fixed before trusting the mechanism**: the `knowledge_record_id`-only signal grouped `qc.006` (general "accuracy within 15%") with `qc.007` (its own LLOQ exception, "accuracy within 20% at the LLOQ") as "jointly applicable" — false, since the two are mutually exclusive circumstances, not concurrent constraints, and the claim's own wording asserted a real contradiction. The verifier correctly caught it. Root cause: a shared `knowledge_record_id` doesn't by itself mean "same circumstance" — a KR frequently bundles a general rule with its own exception. Fixed by requiring the `knowledge_record_id` signal to also have an *equal* (not just overlapping) `condition_ids` set; the `condition_ids`-overlap signal alone already covers genuinely-joint cases like "accuracy ≤20%" + "precision ≤20%" both scoped "at the LLOQ." Two mocked regression tests added for this specific pattern (general-vs-exception NOT grouped; two different parameters sharing one condition ARE grouped).
  - **A second real bug found the same way, on the `KnowledgeRecord` side**: `verifyKnowledgeRecord`'s recomposed `subject action object` claim silently dropped `original_modal_text` entirely (unlike the QC-side fix above) — harmless for `must`/`should` records (whose action text usually already echoes the modal verb), but for a soft modality (`modality=other`, "it is recommended") it recomposed as a bare imperative ("...be demonstrated...") that overstates the source and was correctly rejected (`ich_m10.kr.3_2_5_2.005`). Fixed identically: append `original_modal_text` as a parenthetical when the recomposed claim doesn't already contain it.
  - **Net measured result, same 33-record M10 3.2.5.2 ground truth, two live runs for stability**: 30/33 and 29/33 entailed (previous documented state: 30/33) — kr.005 and the qc.006/qc.007 false-conjunction are now fixed and no longer appear as failures in either run; `qc.010`/`qc.011`/`qc.012` remain reproducibly unresolved across both runs (systematic, not random, consistent with this file's established "reproducible failures are the tractable ones" principle) plus one new non-deterministic single-run item. **Root cause for the persisting 3 is different from what multi-signal grouping was designed to fix**: an ablation test (isolated third-sentence source text vs. the full 3-sentence SourceUnit) showed the correctly-grouped, correctly-worded claim passes in isolation but the model still sometimes imports the *first* sentence's "accuracy within 15%, except at the LLOQ" framing when judging the *third* sentence's differently-scoped "accuracy for QCs in non-accuracy/precision validation runs" criterion — near-identical wording ("accuracy... within 15%") across two unrelated sentences in one SourceUnit, not a grouping/sibling problem. There's also a live question of whether `qc.012` ("accuracy... within 15%") is a well-modeled third record at all, versus a duplicate/redundant split of the tolerance value that `qc.010`/`qc.011`'s own `denominator_or_reference` should carry instead — a data-modeling question, not a verifier-wording one.
