## M1 — Chatbot MVP + extraction/verification pipeline (2026-08-18, in progress)

- Built `engine/`: `data_store.js` (loads+joins all 5 pilot bundles, 153 answerable records), `query_router.js` (Option A structured match, Option B grounded-RAG fallback with mandatory entailment check before showing any answer), `vector_store.js` (keyword-mode default, sqlite-vec embedded vector mode behind the same interface — chosen over LanceDB, which pulled in 109 packages including unrelated image-processing libs and 3 high-severity CVEs; sqlite-vec added only 4 packages, 0 vulnerabilities), `llm_client.js` + `anthropic_adapter.js`/`openai_adapter.js` (provider chosen by which env var is set, never hardcoded), `extraction_agent.js` (schema-constrained, reuses the real `guideline_bundle.schema.json` `$defs`, LLM never assigns archive IDs or generates `source_text`), `verification_agent.js` (narrow entailment check, shared by extraction-time and answer-time verification), `eval_harness.js` (10 gold questions, `test/fixtures/eval_questions.json`), `cli.js`. 172/172 tests pass (`npm test`); `npm run eval` runs in CI at zero API cost (Option A only).
- **Option A fully working end-to-end today, zero LLM calls**: `npm run chat` answers real questions with accurate citations from the 5 pilot bundles.
- **Option B built and unit-tested with a mocked client** (generation → entailment check → refuse-if-not-entailed), but never run against a real model — no API key configured yet.
- Two real bugs found and fixed via actual testing, not just design review: (1) a ranking bug where preferring `QuantitativeCriterion`/`Condition` over `KnowledgeRecord` on "near-max" score used too loose a margin, letting a barely-relevant criterion (score 1) outrank a clearly better-matched record (score 2) — fixed to exact-tie-only preference; (2) `engine/cli.js` raced `process.exit()` against an in-flight async answer when given piped multi-line input, silently dropping output — fixed with an explicit FIFO promise queue.
- Security incident: the user pasted a live OpenAI API key directly into chat. Stored only in local `.env` (now gitignored — `.gitignore` previously had no `.env` entry at all), never echoed back, user was told to treat it as compromised; they revoked and re-issued it themselves outside the chat. `.env.example` documents both provider keys; `.env` holds empty placeholders pending the user filling it in directly (not via chat).
- **Real dry-run measurement (2026-08-18), OpenAI GPT-5.6 Terra, live API, M10 §3.2.5.2 vs. the existing human-reviewed bundle**: extracted 14/14 KnowledgeRecords (record_type 100% match, modality 100% match including the one non-default `modality=other` case), 11/12 QuantitativeCriteria (91.7% recall), 5/7 Conditions (71.4% recall) — **zero fabricated or wrong values across all 30 extracted objects; every failure mode was under-extraction (a real fact missed), never a wrong fact asserted.** The 2 missed Conditions were an idiosyncratic pattern (using `condition_type=applicability` to tag a subsection's scope rather than a true "if X" clause) rather than a dangerous miss. Adversarial check: a deliberately fabricated claim ("accuracy must be within 5%" against a source that says 15%) was correctly caught as `entailed: false` by the verification agent.
- **Open finding, not yet resolved — verification granularity mismatch**: the verification agent, checked against the record's own extracted `source_text` (a deliberately minimal verbatim quote) or even the full source paragraph, flags some *correct* narrowly-scoped criteria as `entailed: false` when they don't restate a sibling exception modeled in a *separate* record (e.g. the general 15%-accuracy criterion doesn't restate the LLOQ 20% exception, which is correctly split into its own criterion per `working_docs/schema.md`'s own "use multiple QuantitativeCriterion records for a general rule plus an exception" guidance) — `claimTextFor()` builds a bare `parameter/comparator/value/unit` string that's narrower than what `query_router.js`'s `formatAnswer()` actually shows users (which includes `denominator_or_reference`). Not patched yet: needs a decision (enrich the claim text vs. relax the verifier's strictness for extraction-time checks vs. accept the current stricter-than-necessary behavior as a safety margin, since it doesn't affect user-facing answers today) rather than a guess. Does not block M1 — this only affects extraction-time dry-run accuracy scoring, not what's shown to end users.
- Real bugs found and fixed via the live API (not just mocks): (1) submitted extraction schema still contained unresolved `$ref`s into a `definitions` block the API never received — OpenAI rejected it outright; fixed with a `dereference()` pass. (2) OpenAI strict-mode JSON Schema rejects `oneOf` (used for nullable `value_fraction`) — rebuilt as `type: ["object","null"]`. (3) GPT-5.6 is a reasoning model: `max_completion_tokens` covers hidden reasoning tokens *and* visible output; the adapter's 1024 default was fully consumed by reasoning on a real section (`finish_reason: "length"`, 0 content characters) — extraction now requests 8000.
- Model choice: GPT-5.6 Terra (not Sol) for extraction — Sol is priced/marketed for "hard problems, long autonomous tasks," not well-scoped single-section structured extraction; escalate only if a real measured accuracy gap (not a guess) shows Terra falling short.
- Remaining before M1 is fully complete per `product_roadmap.md` §3: resolve the verification-granularity open finding above, run Option B against a live model at least once, and decide the dry-run acceptance bar now that a real baseline number exists (KR 100%, QC 91.7%, Condition 71.4%, 0% fabrication rate on this one section).
