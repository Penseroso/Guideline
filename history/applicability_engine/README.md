# Applicability Engine (M6 spike) — archived 2026-08-26

This directory holds the entire "Applicability Engine" explored during the M6 spike: design notes (below, moved verbatim from `docs/milestone_log.md`), the derived binding pipeline, the deterministic evaluator, the RegulatoryContext ontology, rule discovery, and their test suites. **Archived whole, not deleted from git history, following the same precedent as `history/derived_contract/`** — the earlier derived-layer design explored during Phase 3 and archived unadopted. If this direction is needed again, rebuilding fresh against the live schema is expected to be cheaper than reviving this code.

## Layout

All paths below are relative to this directory (`history/applicability_engine/`) — none of them exist at the repo-root path of the same name anymore; the `npm run applicability`/`validate:bindings`/`eval:applicability` scripts that once ran them were removed from `package.json` when this layer was discontinued.

- `engine/`: `applicability.js` (deterministic evaluator), `regulatory_context.js` (RegulatoryContext validation/proposal), `binding_agent.js` (the LLM Condition→predicate binding pipeline), `rule_discovery.js` (keyword-search rule candidates), `applicability_format.js` (finding display), `applicability_cli.js` (formerly `npm run applicability`), `eval_applicability.js` (formerly `npm run eval:applicability`).
- `validation/validate_bindings.js`: schema + referential validation for the binding data (formerly `npm run validate:bindings`).
- `scripts/bind_conditions.js`: the script that ran the binding pipeline live against a document/section slice.
- `data/schemas/condition_binding.schema.json`, `data/derived/condition_bindings/*.json`: the schema and the 71 actual Condition→predicate bindings produced across ICH S6(R1), EMA FIH, and FDA ADA.
- `test/`: the full test suite for all of the above (`engine_applicability.test.js`, `engine_regulatory_context.test.js`, `engine_binding_agent.test.js`, `engine_rule_discovery.test.js`, `engine_applicability_format.test.js`, `engine_applicability_cli.test.js`, `engine_eval_applicability.test.js`, `validate_bindings.test.js`, `fixtures/applicability_cases.json`) — these import from `../../../engine/...` in their original form and will not run as-is from this archived location without path fixes, consistent with `history/README.md`'s "rebuilding fresh... is expected to be cheaper than reviving it."

## What was kept, live, elsewhere (not archived here)

Two improvements this spike surfaced were cherry-picked directly into the live engine, described in full at their real locations:

1. **Korean regulatory-term synonyms** — `engine/text_utils.js`'s `REGULATORY_SYNONYMS` dictionary. Building the RegulatoryContext slot vocabulary below (`program_finding_slots`' `match_terms`) surfaced 14 real Korean regulatory terms (건강인, 환자, 중증질환, 말기질환, 내인성, 외래, 표적, 설치류, 비설치류, 분석, 역가, 중화, and two multi-word phrases already covered by existing single-word entries) that the archive already has matching content for (S6(R1) species selection, EMA FIH patient population, FDA ADA assay tiers) but that the tokenizer's Korean→English synonym dictionary didn't recognize. `가능`/`불가능` (feasible/infeasible) were deliberately left out of the cherry-pick despite appearing in the same vocabulary — too generic in everyday Korean to add as a blanket synonym without real risk of noisy false matches.
2. **`Condition` caveat on every answer** — `engine/query_router.js`'s `formatAnswer`/`formatApplicableConditions`. The audit found that `engine/data_store.js`'s `conditionsByTarget` reverse-index fix (already merged earlier in M6, fixing a dead `kr.condition_ids` read) had made a `KnowledgeRecord`/`QuantitativeCriterion`'s own attached `Condition`s correctly available on every flattened answerable record (`applicable_conditions`), but nothing in the answer-formatting code actually displayed them to the user. Now every Option A/B answer appends the verbatim `condition_text` of any attached `Condition`s as a caveat — never a judgment about whether the condition holds for the reader's situation, which stays out of scope per `docs/project_scope.md`'s non-goals.
3. **Model 0.6.0's document/section scope ontology remains live** (`data/ontology/document_scope_profiles.json`, `engine/data_store.js` `deriveRecordScope`) and **the query-scope routing table** (`data/ontology/context_slots.json`'s `retrieval_slots`, `engine/text_utils.js` `extractQueryScope`) — both predate the discontinued RegulatoryContext/binding layer below and were never part of the decision to discontinue it; they are documented in `docs/schema.md` Model 0.6.0, not here.

## Why discontinued

A real-usage review (prompted directly by a user question — "is this actually more valuable than the existing RAG chatbot yet?") found: the verdict architecture (a four-value applicability judgment, `binding_role`, its own CLI, a separate RegulatoryContext file format) added substantial, ongoing maintenance surface for a coverage island of 71 of the archive's 279 `Condition` records across only 3 guidelines, with no natural-language entry point into the rest of the archive — every prior measurement of this layer had been self-authored by the engineer building it, never touched by a real reviewer. Rule discovery was added specifically to close that entry-point gap and was verified working end-to-end (a plain-language question surfacing relevant rules across two different guidelines with correct, distinct verdicts) — but even with that gap closed, a direct cherry-pick audit found no other piece of the separate verdict/binding architecture that was reusable inside the *existing* answer-a-question pipeline (`engine/query_router.js`) without either duplicating logic it already has (the scope-exclusion check largely re-implemented `query_router.js`'s existing Scope Guard, using the same underlying `document_scope_profiles.json` data) or requiring the full separate RegulatoryContext/predicate apparatus to have any meaning. The two genuinely portable pieces (above) were kept; the rest was archived here rather than maintained as a separate, thinly-used module.

**One idea flagged during the audit but not yet acted on**: the binding pipeline's completeness gate (`engine/binding_agent.js` `checkCompletenessGate`, added after finding 6 of 15 bindable predicates lost real information despite passing entailment) is a portable *pattern* — entailment-only verification structurally cannot catch a claim that silently drops a named alternative or the source's real scope, and this is plausibly also a blind spot in the *existing* extraction pipeline (`engine/extraction_agent.js`/`engine/verification_agent.js`), not just this discontinued layer. Not yet acted on: no audit of the existing 524 `KnowledgeRecord`s for this specific failure mode has been done, and per `docs/schema.md`'s own evidence-first extension policy, that audit should happen before adding a permanent new verification gate to the live pipeline — not the other way around.

## M6 — Regulatory World Model / Applicability Engine spike (2026-08-25 to 2026-08-26, all 10 planned steps complete)

Extends the archive from "search guidelines and answer" toward "given a structured regulatory context, evaluate which rules apply and why," using the existing `Condition` graph (279 records archive-wide) as the evidence base rather than new source extraction. Full design in `docs/schema.md` "Applicability Layer 0.1.0". Deliberately additive: `guideline_bundle.schema.json` and every file under `data/pilots/` are untouched; the layer is independently versioned (`applicability_model_version: "0.1.0"`) and lives entirely under `data/ontology/`, `data/derived/`, and two new `engine/` files, following the same source/derived separation precedent as the archived `history/derived_contract/` layer.

Steps 1-5 of the spike's 10-step implementation order are done (steps 6-10 — running the binding pipeline live on S6(R1)/EMA FIH/FDA ADA, `engine/applicability.js`, `engine/regulatory_context.js`, CLI integration, and the eval harness — remain):

1. **Hardcoded-classifier extraction, both directions, verified byte-for-byte parity before any intentional change.** `engine/data_store.js`'s `deriveRecordScope()` (the Model 0.6.0 document/section classifier) and `engine/text_utils.js`'s `extractQueryScope()` (the Option A/B query-scope classifier) were both table-driven if/else chains hardcoded in JS. Moved to `data/ontology/document_scope_profiles.json` and `data/ontology/context_slots.json` respectively, functions kept as pure lookups over the same signature. Parity verified two ways before trusting either: a full 866-record diff of all 5 scope dimensions across every `KnowledgeRecord`/`QuantitativeCriterion`/`Condition` in the archive (old hardcoded logic vs. new table-driven logic) showed exactly 199 diffs, all in `fda_ada`, all `topic_scope: "general"` → one of 4 new FDA-specific values — the one *intentional* fix bundled into this step (closing the defect where all 132 FDA ADA records fell through to `"general"` because the old chain had no FDA-shaped branch); zero unintended diffs anywhere else. Separately, 52 real (eval fixture + `logs/m2_queries.jsonl`) and synthetic queries were diffed old-vs-new through `extractQueryScope` with zero diffs. `kr.condition_ids` (`data_store.js`, a dead read — the field doesn't exist on `KnowledgeRecord` in the schema, confirmed 0/524 KRs ever had it) was replaced with a real reverse index (`conditionsByTarget`, built from `Condition.applies_to_ids`) — now 194/524 KRs correctly report their applicable Conditions instead of always `[]`; verified nothing downstream reads that field yet, so this is a pure bug fix with no behavior change to any existing answer path.
2. **`data/schemas/condition_binding.schema.json` + `validation/validate_bindings.js` (`npm run validate:bindings`)**: draft-07 schema for a `Condition` → RegulatoryContext-predicate binding, with `binding_role ∈ {full_scope, partial_scope, exception}` schema-enforced against `bindability`/`non_bindable_reason`/`predicate` nullability. The validator adds referential checks ajv can't express: `condition_id` exists in the live archive, `evidence_span` is a verbatim substring of that condition's `condition_text`, and predicate slot/value membership in `context_slots.json`. 11 new tests against synthetic fixtures (not the live archive, so they don't depend on archive content staying byte-identical) plus a manual deliberate-error check (bad `condition_id`, bad `evidence_span`, unknown slot, out-of-vocabulary value, duplicate `binding_id` — all caught).
3. **`engine/binding_agent.js`, the automated binding pipeline** — same extraction/verification separation as the source archive's own pipeline (`product_roadmap.md` §2.5.1), applied here per the user's explicit correction during plan review: the original draft plan hand-seeded S6(R1)'s 30 conditions before extending to EMA/FDA via LLM; changed so **all three slices run through the identical automated pipeline from the start**, with S6(R1) run first only because its conditions are clearest (stabilizing slot vocabulary before the harder slices), not because it's hand-authored. Also incorporates three other corrections from the same review: (a) `not_applicable` is reachable only from a `full_scope` or `exception` binding, never a `partial_scope` one (a `partial_scope` mismatch verdict is `conditional`) — an earlier draft let any bindable predicate evaluating false produce `not_applicable`, which overclaims given only ~71 of 279 archive-wide conditions are in scope for this spike; (b) `conditional` is explicitly defined as "the engine could not deterministically resolve this — human judgment needed," not "the rule is conditional," covering both the non-machine-evaluable-condition case and the new partial-scope-mismatch case under one `conditional_reason`-disambiguated verdict rather than a 5th verdict value; (c) the binding layer's own `verification_status ∈ {verified, needs_review}` is a separate field/vocabulary from the source archive's `review_status`, with no `review_status` field on the binding schema at all, so the two meanings can't be confused even by accident. `full_scope` additionally requires passing a dedicated stricter gate (a separate LLM call weighing sibling conditions on the same rule) before being trusted — demoted to `partial_scope`, never rejected, when that gate isn't confirmed or when the condition has no target rule to be "full scope of" in the first place. 19 new mocked-client tests cover: deterministic-gate rejection short-circuiting before any entailment call, non_bindable requiring no entailment call, entailment failure leaving the binding `needs_review` (kept, not discarded), full-scope demotion (both the no-target-rule case and the gate-not-confirmed case), and `condition_type=exception` always overriding the model's proposed role. A manual end-to-end run (mocked client) through the real `validate_bindings.js` gates against the live S6(R1) archive confirmed a produced binding passes every check.

- **Steps 6-7: first live run of the binding pipeline (S6(R1), all 30 conditions) and `engine/applicability.js`, both against real data, both surfacing real defects fixed before trusting them.** `scripts/bind_conditions.js` (new — a thin runner over `binding_agent.js`, parameterized by `document_id` + optional `section_number` filter, reused unchanged for the EMA/FDA slices) ran the pipeline live against the real OpenAI-backed archive. First run: 16/30 `verified`. Root cause (`claimTextForBinding`): the claim interpolated a slot's long `description` sentence as a noun phrase and asserted "applies only when X" exclusivity the condition text never states — the verifier correctly rejected 13/13 bindable proposals for introducing an unsupported enum token and framing. Fixed by adding `value_labels` (short natural-language paraphrases) to `context_slots.json`, rephrasing the claim as a neutral "describes the following circumstance," and checking entailment against the binding's own `evidence_span` rather than the full `condition_text` (narrowing the check to exactly the interpretation risk that matters — the same "separate, narrower verification" principle §2.5.1 already established). Second run surfaced a second, more serious bug in `resolveBindingRole`: checking `condition_type="exception"` before `bindability` forced `binding_role="exception"` even when the model correctly proposed `non_bindable` for a condition whose source `condition_type` happens to be structurally "exception" but whose actual wording ("unless there is a scientific rationale for using non-rodents") is an expert-judgment hedge, not a checkable predicate — both a schema-invalidity bug (`non_bindable` requires `binding_role=null`) and a correctness bug (it would have let an unverifiable hedge deterministically flip a verdict to `not_applicable`). Fixed by checking bindability first. Third run surfaced a third bug: a gate-caught incomplete proposal (`bindability="non_bindable"` with `non_bindable_reason` omitted) was still persisted with `non_bindable_reason: null`, schema-invalid, even though `verification_status` correctly read `needs_review`. Fixed by adding `finalizeBindingShape()`, which guarantees the persisted shape is always structurally schema-valid regardless of what the model proposed, while the deterministic gate still grades the model's raw proposal for `verification_status` — mirroring `engine/pipeline.js`'s own established separation for the source archive. Final S6(R1) result: **24/30 `verified`, 6/30 `needs_review`, 0 schema violations** (`npm run validate:bindings`), `binding_role` distribution `{partial_scope: 12, null: 18}` (no `full_scope`/`exception` proposals survived this particular run — expected run-to-run variance, not a design gap). `engine/applicability.js`'s own implementation review (not a live-run failure) caught two further gaps before any live use: the injected `bindingsByConditionId` test seam was shadowed and silently ignored, and the plan's explicit guard — a `needs_review` binding must be exposed in `basis` but must never itself produce `not_applicable` — was never implemented; both fixed, with a new `conditional_reason="unverified_binding"` covering the latter. Full design write-up and the finalized `conditional_reason` enum (4 values, 2 added during implementation) are in `docs/schema.md` "Applicability Layer 0.1.0". End-to-end sanity checks against the real S6(R1) data confirmed the exact intended behavior: a two-species condition (`cond.part2.2_2.001`, `binding_role=partial_scope`) evaluated against a mismatching context (`relevant_species_availability=one`) correctly returns `conditional`/`partial_scope_mismatch`, never `not_applicable`.

### Binding semantic audit + pipeline hardening (2026-08-26, post-M6)

A manual semantic audit read all 15 bindable predicates and their source `condition_text` side by side (not just their schema/entailment status) and found **6 of 15 (40%) had real information loss** despite every one passing the entailment gate — entailment only catches an ADDED unsupported claim, never a DROPPED one, so a predicate naming only one of several alternatives, or asserting an already-true-anyway background fact instead of the source's real conditioning language, sails through unflagged. Concretely: `cond.part2.2_1.005` used `operator: "equals"` with only `monoclonal_antibody`, silently dropping the source's own "and other related antibody products"; `cond.part2.notes.003`/`.004` bound a status/history fact ("a TCR study will be/has been conducted") to `tcr_study_feasible`, a slot about POSSIBILITY, not history; `cond.part2.notes.005` bound only `product_modality=adc` — true, but tautological in an ADC-only subsection, capturing none of the source's actual condition ("if two species have been used"). Separately, cross-referencing all 56 `non_bindable` classifications against `verification_status` found that **all 4 `non_bindable`+`needs_review` cases were exactly the ones independently flagged as likely ontology gaps** — the model's own uncertainty signal (needs_review even on a non_bindable call) turns out to be a usable, evidence-based prioritization signal for where the RegulatoryContext vocabulary is actually missing something, not just where the source text is genuinely a hedge. Recorded as a standing discovery heuristic for future ontology work: **check `non_bindable` + `needs_review` first.**

Fixed, in order:

1. **`engine/binding_agent.js` gained a fourth gate, completeness** (`checkCompletenessGate`), run after entailment passes and before `full_scope`/verification — the complementary question entailment structurally cannot ask: does the predicate's restatement omit a named alternative or the source's real conditioning fact? Deliberately checked against the full `condition_text`, not `evidence_span` — `evidence_span` is the model's own selection and can itself be the too-narrow thing (one binding's `evidence_span` was the single word "ADC," trivially "complete" relative to itself). A completeness failure produces `needs_review` with the missing aspect recorded in the parallel `reasons` output, same status semantics as an entailment failure.
2. **Three targeted rules added to the extraction system prompt** (`systemPrompt()`), each naming the exact live failure it was written to prevent (not a generic instruction): capture every named alternative via `operator: "in"` rather than picking one; never bind a status/history statement ("has been done," "will be done") to a feasibility-type slot; and check before finalizing whether a predicate would already be true for virtually every condition in the same section (a tautology), in which case look for the source's real conditioning fact instead or mark `non_bindable`.
3. **Re-ran the full pipeline live across all three slices** (71 conditions) with both fixes active. All 4 originally-flagged bindings now resolve correctly: `cond.part2.2_1.005` now uses `operator: "in", value: ["monoclonal_antibody", "other"]` (captures both named alternatives instead of dropping one); `cond.part2.notes.003` dropped the `tcr_study_feasible` misuse and now asserts only `product_modality=bispecific_antibody`; `cond.part2.notes.004` and `cond.part2.notes.005` are now correctly `non_bindable` (`narrative_reference` / `expert_judgment_required`) rather than asserting a misleading or tautological predicate.

New measured baseline (down from the initial-scope numbers above, and **expected, not a regression** — trading verified-rate for honesty is the explicit point of adding a stricter gate, the same calibration story as this project's own QC entailment-tightening history): bindable 13/71 (18%, was 21%), verified 56/71 (79%, was 85%). Slots actually used by a bindable predicate dropped to 5 (`assay_tier`, `product_modality`, `relevant_species_availability`, `target_nature`, `conjugated_toxin_novelty`) since `subject_population` and `tcr_study_feasible` no longer appear in any surviving predicate — both were exactly the misused/tautological cases now correctly reclassified, not a loss of real capability. **The "0 new slot types" finding holds, and is now stronger**: the tightened pipeline needed zero new slot types to correctly *decline* four previously-loose bindings, using only the same closed vocabulary.

One notable side effect, recorded honestly rather than chased further (consistent with this project's own documented anti-pattern of over-tuning against small samples without a multi-section eval): a few previously-clean bindings shifted to `needs_review` or `non_bindable` on this re-run (e.g. `fda_ada.cond.IV_A_1.007`, a clean `assay_tier=confirmatory` match, flipped to `non_bindable`) — plausibly the stricter "avoid tautological predicates" framing making the model more conservative, plausibly ordinary run-to-run variance; not distinguishable from one run, and not worth a second live pass to disambiguate right now.

`test/fixtures/applicability_cases.json` regenerated against the new live data (30 cases, up from 29 — added two cases specifically regression-testing the notes.004/notes.005 fixes) — 11 of the original 29 expected values changed, every one traced to a specific, understood binding change above, none to an `applicability.js` defect.

216/216 tests pass (`npm test`, 6 new: 2 for `checkCompletenessGate`, 4 sequential-client responses added to existing full_scope-gate tests); `npm run eval` 18/18 unchanged; `npm run validate:pilots` 5/5 unchanged; `npm run validate:bindings` 3 files/71 bindings/0 errors; `npm run eval:applicability` 30/30.

### Context ontology v0.2 (2026-08-26)

Evidence-first promotion, per `docs/schema.md`'s extension policy: only the audit finding that cleared a 2+ occurrence bar was promoted. Added `disease_severity` (`data/ontology/context_slots.json`, `program_finding_slots`) with values `general | severe_or_life_limiting`, evidenced by 3 EMA FIH §7.3 Conditions (`cond.7_3.006`, `.007`, `.011`) independently stating the same "advanced cancer / life-limiting disease" distinction. Explicitly deferred, documented so the reasoning isn't lost before the next audit:

- **Prior healthy-volunteer data, multi-domain product, high-homology protein family** — each appeared only once (high-homology twice, but as the identical sentence copy-pasted across two `applies_to_ids`, not independent evidence) in the current 71-condition sample, below the promotion bar. Multi-domain in particular is likely to clear it once FDA ADA §IV.A.2/A.3 (currently `BACKLOG`, `docs/coverage_fda_ada.md`) are extracted — re-check then, not now.
- **Assay-level statistical behavior** (`fda_ada.cond.VI_B.002/004/005/006` — mean/variance patterns for cut-point methodology selection) clears the occurrence bar (4 conditions) but was deliberately NOT folded into RegulatoryContext's `program_slots`/`program_finding_slots` — it describes a property of an *assay's data*, not the *program*, a different axis than every other slot in the vocabulary. Left as an open design question (does the Applicability Engine need a second context category, e.g. `assay_data_state`, or is this permanently out of scope as a data-analysis question rather than a regulatory-context one) rather than force-fit into the existing categories.

### Rule discovery — minimum viable evaluation path (2026-08-26)

**Context for this step**: a mid-development review raised a fair, direct challenge — is the Applicability Engine actually more valuable than the existing RAG chatbot yet? Answer at the time: no. Without a way to find a rule_id from a natural-language question, nobody but the engineer building it could use the tool at all; every prior M6 measurement was self-authored, never touched by a real reviewer. Two paths were considered: finish every planned feature (modality-aware verdict framing, full chat routing) before any real evaluation, or build only the minimum needed to let one real question reach `evaluateRule()` and get real feedback before investing further. Chose the second, deliberately deferring modality-aware framing and chat-level question routing — both are refinements, not blockers to a first real look.

`engine/applicability_cli.js`'s `evaluate` subcommand gained a `--question "<text>"` mode (alongside the existing explicit `--rules <ids>`), implemented by reusing `engine/vector_store.js`'s existing keyword search unmodified — restricted to `knowledge_record`/`quantitative_criterion` records only (Condition entries are evidence attached to a rule, never a rule to evaluate themselves). Zero new LLM cost, zero changes to `vector_store.js`/`query_router.js` — the same primitive Option B already uses for retrieval, repurposed to surface rule_id candidates instead of an answer.

Manually verified end-to-end against real data: `node engine/applicability_cli.js evaluate --context <file> --question "species selection when no relevant species exists" --top 3` surfaced 3 topically relevant rules spanning **two different guidelines** (`ich_s6_r1.kr.part1.3_3.009`, `ema_fih.kr.7_2.003`, `ich_s6_r1.kr.part2.2_1.009`) from one plain-language question, each evaluated against the given context with a distinct, correct verdict (`applicable`, `conditional`/`non_bindable_condition`, `conditional`/`unverified_binding`) and real citation — the first real demonstration of the full "natural question → candidate rules → context-aware verdict" flow this milestone's underlying vision described, achieved without touching either of the two existing engine files it depends on.

222/222 tests pass (`npm test`, 6 new); `npm run eval` 18/18 unchanged; `npm run validate:pilots` 5/5 unchanged; `npm run validate:bindings` 3 files/71 bindings/0 errors unchanged; `npm run eval:applicability` 30/30 unchanged.

Deliberately not done (deferred pending real reviewer feedback on this minimum path, not abandoned): modality-aware verdict framing (combining `KnowledgeRecord.modality` — must/should/may — with the verdict to produce a Required/Recommended/Conditional framing), and automatic Evidence-question-vs-Applicability-question routing inside `npm run chat` itself. Both remain separate, explicit tools (`npm run chat` for evidence Q&A, `npm run applicability` for context-aware evaluation) until real usage says which refinement, if any, is worth building next.
